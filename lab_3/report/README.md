### Цель и задание

Освоить создание и синхронизацию потоков. Отсортировать массив целых чисел битонической сортировкой. Максимальное число одновременно существующих потоков задавать ключом запуска. Показать фактическое число потоков средствами Linux и исследовать ускорение и эффективность при разных входных данных.

### Архитектура решения

Программа на C читает из `stdin` длину массива и его элементы. Предел потоков задаётся ключом `--threads`; главный поток тоже сортирует, поэтому при пределе 4 создаются три рабочих потока. Результат выводится в `stdout`, PID, TID и время сортировки — в `stderr`.

Битоническая сеть требует длину, равную степени двойки. Программа создаёт временную копию массива, дополняет её значениями `INT_MAX`, выполняет сортировку и возвращает первые `N` элементов. На каждой стадии все потоки обрабатывают разные диапазоны индексов. `pthread_barrier_t` не позволяет перейти к следующей стадии, пока не завершились все сравнения текущей. Перед началом работы созданные потоки ждут сигнал от главного потока; это позволяет корректно завершить их, если создание одного из следующих потоков не удалось. В конце главный поток вызывает `pthread_join`.

```text
stdin → массив → дополнение до степени двойки → сравнения по стадиям → stdout
                                                   ↑
                                 главный + рабочие потоки, барьер между стадиями
```

Разбор ввода и ключей находится в `../src/main.c`, сортировка и работа с потоками — в `../src/bitonic.c`.

### Ключевые фрагменты кода

Партнёр элемента `i` находится по индексу `i ^ j`. Каждая пара обрабатывается один раз:

```c
size_t partner = i ^ j;
if (partner < i)
    continue;

int ascending = (i & k) == 0;
if ((ascending && shared->values[i] > shared->values[partner]) ||
    (!ascending && shared->values[i] < shared->values[partner])) {
    int temporary = shared->values[i];
    shared->values[i] = shared->values[partner];
    shared->values[partner] = temporary;
}
```

После сравнений одной стадии поток ждёт остальных:

```c
compare_range(shared, id, k, j);
if (shared->threads > 1) {
    int error = pthread_barrier_wait(&shared->barrier);
    if (error != 0 && error != PTHREAD_BARRIER_SERIAL_THREAD)
        check_thread(error, "pthread_barrier_wait");
}
```

### Сборка и проверка работы

Из каталога `lab_3`:

```sh
make
printf '7 9 -2 4 4 0 7 -8\n' | ./build/bitonic --threads 3
```

В Linux получен результат:

```text
[pid 25 tid 25] main
[pid 25 tid 26] worker 1
[pid 25 tid 27] worker 2
count=7 threads_used=3 sort_ms=0.159167 sorted=yes
-8 -2 0 4 4 7 9
```

Для проверки числа потоков использован ключ `--pause 3`. Во время паузы вывод `/proc/23/status` показал `Pid: 23`, `Threads: 4`; команда `ls /proc/23/task | wc -l` также вывела `4`. В журнале программы были TID 23, 25, 26 и 27. При разработке результат сверялся с эталонной сортировкой на массивах разных длин, включая длины не степени двойки, повторения и граничные значения `int`.

### Исследование производительности

Замеры сделаны в Linux-контейнере Debian 13 (aarch64), GCC 14.4.0, доступно 8 логических процессоров. Входные файлы были подготовлены до запуска программы и повторно использовались для всех значений числа потоков. Случайные значения получены генератором xorshift32 с зерном 42 в диапазоне от −1 000 000 до 1 000 000. Для каждого сочетания сделано три запуска; в таблицах приведена медиана времени сортировки. Для короткого массива накладные расходы на запуск стадий и ожидание барьера сравнимы с полезной работой, поэтому 8 потоков медленнее одного. На миллионе элементов четыре потока ускоряют сортировку примерно в 3,27 раза. При переходе к восьми потокам выигрыш небольшой; вероятные причины — расходы на синхронизацию и конкуренция за память. Сеть выполняет одинаковое число стадий независимо от порядка входа, но число обменов и поведение ветвлений различаются. Это может объяснять более короткое время для упорядоченного и обратного массивов. Замеры в контейнере также зависят от нагрузки хоста.

### Вывод

Реализована битоническая сортировка с ограничением числа потоков через ключ запуска. Корректность проверена на обычных и граничных входах, фактическое число потоков подтверждено через `/proc`. Параллельная обработка ускоряет сортировку крупных массивов, но для коротких накладные расходы на синхронизацию могут перевесить выигрыш.
